## 这次改变了什么

此前每条连接只有一条读取循环，所有宿主回调都在该循环内串行 `await`；回调内等待附加包回复会
阻塞唯一读取者并最终超时（R00 已固定为严格预期失败）。

现在新增**显式启用**的可靠调度路径：

- `config.DispatchSettings.mode`：`"legacy"`（默认）或 `"reliable"`。旧入口不改变任何行为。
- `gateway/dispatch.py`：`BusinessDispatcher` 持有有界队列、并发上限、按 lane 的 FIFO 锁、
  计数器与任务回收。`submit()` 永不等待；队列满或已关闭时返回 `False` 并记录
  `business_queue_overflow` / `business_submit_after_close`。
- `gateway/runtime.py`：每条连接一个 `ConnectionRuntime`，分组业务调度器与观察调度器。
- `server_facade.py`：可靠模式下读取循环只做解析、请求配对和分片重组；宿主回调提交到业务
  调度器，事件提交到观察调度器。连接建立回调使用 `connection` lane；玩家消息和 UI 消息使用
  `player:<name>` lane；无玩家身份的控制消息使用 `control` lane。
- 业务任务、观察任务和事件任务都由 SDK 持有，断连时统一取消并等待退出。

回调执行顺序（可靠模式）：

1. 握手、订阅通过发送路径完成后，提交 `CONNECTED` 事件与 `on_connected` 业务任务；读取循环
   不等待二者。
2. 每个入站帧先提交 `RAW_INBOUND` 观察事件，再在读取循环内完成解析。
3. `commandResponse` 在读取循环内完成 SDK 请求配对，然后提交事件与 `on_command_response`。
4. 附加包分片在读取循环内重组并完成请求配对；UI 回调、控制回调提交到业务 lane。
5. 玩家消息按 `player:<sender>` lane 串行；不同玩家可并发。
6. 断连：关闭附加包会话 → `drop_connection` 关闭 runtime（失败请求、取消任务、关闭发送）
   → `on_disconnected` 仍以内联方式等待（它不在业务队列中，不会被提前取消）。

边界：异步等待不会自动解决 CPU 密集的同步代码。宿主若在回调内执行阻塞计算，仍会占用事件
循环；这类工作应由宿主移出事件循环。本项不改变线格式。

## 复核修复（2026-10-31）

主代理复核指出 R01-2/R04-1 的调度边界不满足：`dispatch.py` 在等待 lane 锁之前
先取全局 semaphore。`max_concurrent=2` 时，A1 暂停并占住 lane A，A2 虽未运行却占住
第二个 slot 并等待 lane A，B1 无法启动。

修复（`17f0535`）：

- 每个 lane 使用独立 FIFO 桶；只有可立即运行的 lane 才进入 round-robin ready 环。
- 全局并发上限由 supervisor 的 `active < max_concurrent` 控制；被暂停 lane 的排队项
  不再占用 slot。
- 同 lane FIFO、不同 lane 并发、关闭时任务/计数/lane 清理保持不变。

先复现后修复：新增
`test_paused_lane_does_not_consume_concurrency_slot`，在旧实现上以
`TimeoutError` 失败，修复后通过；另加
`test_ready_lanes_run_round_robin` 固定 lane 轮转顺序。未通过调大 `max_concurrent`
或无限任务规避。

本项未修改线格式、旧入口默认值或 `mode="legacy"` 行为。MCBE 实机仍未验证。

  无需回滚协议。
