## 这次改变了什么

新增 `gateway/sender.py::OutboundScheduler`，每条连接一个：

- **单一出口**：可靠路径的握手、订阅、原生命令、文字、脚本事件、附加包消息都经
  `scheduler.send()`；只有该调度器的 worker 调用底层传输。`state.send_payload` 被替换为
  调度器适配器，宿主/`McbeOutboundDelivery` 的现有调用自动进入调度器。
- **容量**：按帧数与 UTF-8 字节总量双重限制。`CONTROL` / `REQUEST` 在满时受控等待
  `capacity_timeout` 后抛 `SendQueueFullError`；`BULK` 立即抛错，不无限补救。
- **优先级**：`CONTROL`（握手/订阅）> `REQUEST`（请求/回复）> `BULK`（长内容）。长传输期间
  控制帧与短回复仍有发送机会；同一逻辑消息由调用方逐帧 `await`，内部顺序不变。
- **限速**：`min_interval_seconds` 按连接总量执行，可注入时钟与 sleep 以便模拟验证；多开
  发送任务无法绕过，因为只有一个 worker 调传输。
- **失败语义**：传输异常先传播给所属帧，再失败该连接剩余排队帧并关闭调度器；其他连接各有
  调度器，不受影响。超长原生命令仍由 `FlowControlMiddleware` 抛 `FrameTooLargeError`。
- **关闭**：`close()` 幂等，唤醒所有等待容量的发送者，失败剩余帧；关闭后的发送抛
  `SendClosedError`。

`ConnectionRuntime` 负责把调度器、请求表、命令客户端和调度器适配器组合在一起；
`ConnectionManager.drop_connection` 在断开时关闭 runtime。

## 复核修复（2026-10-31，`26fa23a`）

复核确认初版调度只覆盖了队列机制，真实生产路径没有实际使用类别、公平与受限预留：

1. **类别贯通**：`ConnectionRuntime.send_from_host` 与 `scheduler.send_from_host`
   一律使用 `REQUEST`，`McbeOutboundDelivery` 只有一个发送回调，因此生产环境
   从未产生 `BULK`。现在：

   - `McbeOutboundDelivery` 新增可选 `send_bulk`，签名仍是
     `Callable[[str], Awaitable[None]]`；tellraw / scriptevent 分片（含
     `McbewsV1Delivery` 文本响应）走 bulk，原生命令与通用 payload 走 request。
   - 可靠运行时在 `ConnectionState.send_bulk` 安装 bulk 适配器；
     `state.send_payload` 保持旧的单参数合同，legacy 路径不设置 `send_bulk`。
   - `examples/addon-server` 传入 `send_bulk=state.send_bulk`。
   - 集成回归 `test_send_priority_integration.py` 通过真实
     facade + delivery + runtime + `command_client.run()`，验证两个长 tellraw
     排队为 `BULK`、命令为 `REQUEST`；旧实现该场景全部为 `REQUEST`。

2. **控制预留（数量与字节）**：`_has_room` 原来所有优先级共用容量。现在
   `control_reserve_slots` / `control_reserve_bytes`（默认 1 / 4096，并限制为至少
   留出 1 个非控制帧或 1 字节）只允许 `CONTROL` 使用。`max_queue=2` 且 bulk 在途
   时，第二个 bulk/request 被明确拒绝，`CONTROL` 仍可入队并紧随在途帧发送，不再
   排在 bulk 之后。回归：
   `test_control_reservation_keeps_queue_room_for_control_frames`、
   `test_control_reservation_covers_bytes_as_well_as_frame_count`。

3. **公平规则**：严格优先级会让低优先级无限等待。新增 `fairness_quota`（默认 8）：
   高优先级连续发送达到配额后，服务一次最高优先级的“饥饿”层级；同级仍 FIFO。
   回归 `test_sustained_control_traffic_does_not_starve_bulk` 用持续 control 流量
   验证 bulk 在第 4 个 control 前被发送，而不是无限延后。

4. **总等待截止时间**：`_admit` 原来每次容量通知都重新调用
   `wait_for(..., capacity_timeout)`，通知风暴可无限延长等待。现在在进入等待前计算
   一次总 deadline，后续通知只重新检查剩余时间。回归
   `test_admission_deadline_is_not_reset_by_notifications` 在持续 `notify_all`
   下仍按总时限抛出 `SendQueueFullError`。

5. **测试数量更正**：原记录写“17 passed（8 + 9）”有误。基线 `cdb2e27` 实际为
   `18（test_outbound_scheduler 8 + test_reliable_facade 10）`；R03 修复后为
   `22（12 + 10）`。Coordinator 追加的 R01/R04 证据（三 hook 参数化 + 关闭窗口
   2 个用例，`ec1d3e4`）使最终快照为 `27（12 + 15）`。以最终快照为准。

旧入口默认值未变：`DispatchSettings.mode="legacy"`、`min_interval_seconds=0`；
新增配置均有默认值并在 `examples/addon-server/README.{md,zh.md}` 记录生产启用依据。
未修改线格式。MCBE 实机仍未验证。

## 剩余问题与回退

- 默认不限速；需要限速的部署通过 `gateway.send.min_interval_seconds` 显式开启。
- 生产启用依据已写入 `examples/addon-server/README.md` / `README.zh.md`：只切换
  `dispatch.mode="reliable"`，其余使用 `GatewaySettings()` 默认值；这些值尚无 MCBE
  实机证据，R18 统一测量。
- 未覆盖：Python 版本矩阵、websockets 12／14／16、MCBE 实机与 Beta APIs、分发包构建。
- 回退：保持 `mode="legacy"` 即不创建调度器；可靠路径可单独降低 `queue_maxsize` 复现旧式
  过载行为。
