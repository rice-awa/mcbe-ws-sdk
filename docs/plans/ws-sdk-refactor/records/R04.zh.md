## 这次改变了什么

- **玩家隔离与顺序**：`BusinessDispatcher` 按 lane 串行；facade 用 `player:<sender>` 区分玩家，
  同一玩家 FIFO、不同玩家并发。无玩家身份的控制消息（`on_error`、`on_command_response`、
  无身份附加包控制帧）进入 `control` lane，不会被误归入某个玩家队列。
- **世界资源顺序**：`ConnectionRuntime.lane(name)` 暴露共享 FIFO 锁。需要顺序修改同一世界资源
  的宿主操作使用同一名称（例如 `world`）；只读/独立操作可使用不同 lane 并发。
- **关闭流程**：`ConnectionManager.drop_connection` 先从活动表移除连接、取消响应发送任务，再
  关闭 runtime（失败请求 → 取消业务/观察任务 → 关闭调度器），最后发出 `DISCONNECTED`。关闭
  幂等；关闭后的发送抛 `SendClosedError`，请求登记抛 `RequestClosedError`。
- **残留清理**：runtime 关闭后清空 lane 表、请求表、任务集合与调度器队列；附加包会话在断开时
  关闭并失败挂起请求。重复连接不会继承旧连接的回包或请求。
- **附加包串行调度**：`addon/scripts/bridge/router.ts` 增加 `MAX_ACTIVE_REQUESTS = 64` 上限
  与 `droppedActiveRequests` 计数；慢处理器不再形成无界 Promise 链。就绪前的
  `MAX_PRE_READY_REQUESTS = 64` 保持不变。

## 复核修复（2026-10-31，`062acd9`）

复核确认 `ConnectionRuntime.close` 的 guard 只包住 `_closed`：第一次 close 内联执行
清理；第二次 `await close()` 看到 `_closed` 直接返回，此时业务任务可能仍在取消、
scheduler 尚未关闭（`task_count=1`）。若第一次调用的等待者被取消，清理会停在
`business.close()` 的 `gather` 中，调度器/等待表/队列留下半成品。

修复：

- 第一次 close 只负责创建并记录一个 `_close_impl` 任务；之后所有 close 都
  `await asyncio.shield(同一个任务)`。
- 并发 close 不会提前返回；取消某一个等待者不会取消清理任务。
- 清理完成后，业务/观察任务、请求表、lane 表、发送队列与缓冲全部归零/关闭。

回归（`tests/unit/test_runtime_close.py`，全部以显式事件门控）：

- `test_concurrent_close_calls_wait_for_the_same_completion`：第二次 close 在
  第一次完成前不得 done，释放被取消的业务任务后两者一起完成。
- `test_cancelling_one_close_caller_does_not_stop_cleanup`：取消第一个等待者后
  清理继续；之后再次 `close()` 观察到完全清理状态。

两个用例在旧 guard 实现上均失败。

同批复核还发现“先 pop 活动连接、后标记 runtime closed”的发送竞态（`ec1d3e4`）：
`ConnectionManager.drop_connection` 先从 `_connections` 移除连接，此时 runtime 尚未
关闭；`_wrap_send` 找不到 state 时静默 `return`，调度器会把这次传输计为成功，上层
请求误以为已发送。可靠模式现在在该窗口抛出 `SendClosedError`，让所属请求/发送观察到
失败；legacy 路径按原合同继续静默跳过。回归
`test_send_during_drop_window_fails_instead_of_reporting_success` 在旧实现失败，
`test_legacy_send_during_drop_window_keeps_best_effort_behavior` 固定旧行为。

未修改线格式。MCBE 实机仍未验证。

## 第二轮定点修复：manager 共享清理（2026-10-31）

执行者为本次新开的受监督 Codex，会话起点 3397b3ac107ee8577bba06edec53de7b585f8a72，
分支 refactor/ws-sdk-refactor，起始工作区干净；保留 c7b4d32 规范与此前修复，不开始 R05。

根因是 public manager 先 pop 活动连接，再等待 sender/runtime，后续 drop 与 shutdown 看不到
已移除连接；runtime 内的共享 close 不能替代 manager 边界的完成等待。
现每连接登记独立清理任务，所有外部 drop 等待其 shield；等待者取消不会再次取消 sender，
也不会跳过 runtime／legacy 请求清理。shutdown 合并活动连接和在途清理，完成回调移除任务表
并读取异常；DISCONNECTED 仍在 sender、runtime／请求清理之后且仅发一次。
事件观察者重入 drop／shutdown 保持旧幂等行为，避免清理任务等待自身。

回归使用事件控制业务／sink 的取消退出、第二个 drop 与 shutdown 入场、facade finally 入场：

- test_concurrent_manager_drops_wait_for_runtime_cleanup：并发 drop 及取消首等待者，两变体。
- test_cancelled_drop_during_sender_cleanup_is_joined_by_shutdown：取消发生在 sender 退出期间，
  legacy／reliable 两变体；另一个连接也关闭，请求终止且 DISCONNECTED 顺序与次数正确。
- test_disconnected_observer_can_repeat_drop_without_changing_order：旧观察者重入无死锁。
- test_facade_disconnect_joins_cancelled_manager_drop：真实 facade 断开等待已有 manager 清理，
  on_disconnected 仅在 runtime 完全回收后执行。

前两组与位置参数兼容用例在原实现首次运行共 5 failed（未添加 cancel_first 参数化时）；
证据为第二个 drop 已 done、取消被 sender await 吞掉、queue／runtime 位置绑定错误。
