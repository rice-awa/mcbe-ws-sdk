# R18 同环境合成性能比较

执行日期：2026-10-31。结论：**字节和包数不变；兼容收发路径的微基准变慢，不能宣称提速。**
这份证据不代替游戏内性能验收，也不衡量新入口在并发请求下的吞吐。

## 方法

从 R00 提交 `39aaf9e` 取出 `src`，放入 `/tmp/r18-r00-reference`。
用该提交的同一份 `tools/benchmark_baseline.py` 分别加载旧源码与本轮候选源码。
执行顺序为旧版、候选，二者使用同一个 Python 3.14.4、相同依赖与机器。
原脚本保存为 [harness.py](harness.py)，参数及摘要见 [method.json](method.json)。

每场景运行五轮，每轮 30 次，中文与表情输入为 4096 个 UTF-8 字节，命令预算 461 字节。
每个场景另运行一次相同负载，用 `tracemalloc` 测量内存峰值。
为缩短发布准备时间，本轮将每轮次数由历史 R00 的 200 次减为 30 次，**双方同时使用 30 次**；
不直接比较历史报告的绝对时间。运行期间还有文档和子代理工作，时间存在调度噪声。

实际执行使用仓库 `.venv/bin/python`，工作目录为 `/tmp`，分别设置
`PYTHONPATH=/tmp/r18-r00-reference/src` 与本仓库的 `src` 路径，执行：

```text
python /tmp/r18-baseline-harness.py --runs 5 --messages 30 --payload-bytes 4096 --command-budget 461 --out <baseline.json 或 candidate.json>
```

两个命令均退出 0。[旧版原始数据](baseline.json)与[候选原始数据](candidate.json)包含依赖版本与逐轮结果。
本地可编辑安装的版本元数据仍为 `0.1.0`，因此这些 JSON 的包版本字段不是候选标识；
源码由路径选择，候选身份由 R18 分发包 SHA-256 确认。

## 结果

耗时单位为毫秒。收包为每帧处理耗时，出站为排队至响应接收器处理的延迟。

| 场景 | 旧版中位数／95 分位 | 候选中位数／95 分位 | 中位数变化 | 内存峰值：旧版／候选，字节 |
| --- | --- | --- | --- | --- |
| 文字分片 | 84.779／210.442 | 68.630／96.207 | -19.05% | 60837／60837 |
| 兼容路径收包 | 0.08481／0.15543 | 0.22797／0.40329 | +168.80% | 39329／40009 |
| 兼容路径出站 | 0.57219／0.96075 | 1.33106／2.75825 | +132.63% | 22897／23393 |

分片两端每条逻辑消息均为 12 个命令、7999 个完整 WebSocket 载荷字节；
每轮 360 个命令、239970 字节，预算与内容相同。
收包原始载荷均为 9326 字节；出站队列容量均为 31。
这些是合成场景的统计，不是实际网络流量、游戏帧率或背包查询耗时。

旧版／候选的逐轮吞吐变化范围分别为：分片 58.96%／30.50%，收包 33.67%／19.45%，
出站 58.30%／93.45%。分片变快处于明显噪声中，不作为改进结论；收发中位数退化不能仅归于波动。

## 原因核查与处理

使用相同解释器和脚本，额外用 `cProfile` 运行十轮、每轮 200 条收包和 200 条出站；
不测分片。统计文本见 [旧版调用剖析](baseline-profile.txt)与[候选调用剖析](candidate-profile.txt)。
剖析会增加测量开销，其绝对耗时不与上表混用。

- 对 2000 条入站帧，旧版调用 2000 次 JSON 解码，候选调用 4000 次：追踪分类与业务路由各解码一次。
- 候选在收包和响应发送时建立追踪作用域；剖析新增 `trace_scope`、数据类复制、上下文变量及追踪编号生成开销。
- 候选共约 48.8 万次函数调用，旧版约 20.5 万次；新增追踪与事件路径解释了主要额外成本。

本轮保留已经验收的追踪和回调合同，不为微基准临时关闭功能、改变旧默认值或加入未经验证的优化。
上述成本作为公开的验收限制保留，R18 的游戏同条件比较仍未完成；发布和默认值切换均不推进。
如游戏实测显示影响可感知延迟，后续先单独验证“共用已解码数据”能否保留原始观察和追踪顺序，
再决定优化；不能据此直接省略追踪或重放世界命令。
