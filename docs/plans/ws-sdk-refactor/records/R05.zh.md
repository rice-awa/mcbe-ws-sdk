## 这次改变了什么

- **Python 内部注册表**：新增 `mcbe_ws_sdk.capability.CapabilityRegistry`，按名称注册
  处理器与可选输入校验器，`dispatch()` 返回处理器结果或结构化
  `UNSUPPORTED_CAPABILITY` / `INVALID_REQUEST` / `CAPABILITY_FAILED`。本阶段只提供内部
  注册能力，不接入附加包反向能力帧；该线协议路径仍属 R12。
- **附加包路由表**：新增 `bridge/capabilityRegistry.ts`；`registerCapability` /
  `unregisterCapability` 与内置能力共存，无需修改 `router.ts` 的分支。
- **默认注册**：`capabilities/index.ts` 保留旧 `defaultCapabilityRegistry` 表的形状，
  并新增只含内置能力的注册表工厂与复位辅助；两个内置能力在处理器前校验
  `payload.target` 必须是字符串。
- **旧总处理器**：`setCapabilityHandler` 的覆盖语义不变——设置后接收所有能力，
  不查询内置注册表；兼容测试固定该行为。

注册与分发规则：

1. 重名默认抛错；`replace: true` 才覆盖。
2. 旧注册句柄不能移除替换后的同名注册；注销只匹配当前条目的对象身份。
3. 分发在开始前捕获当前条目：调用中途注销/替换不影响本次调用，后续调用看到新状态。
4. 校验器先于处理器；未知名称、无效输入、校验器/处理器异常均返回结构化结果，
   不影响其他注册项。

## 主代理复核发现与修复（`9c405ba`）

主代理 Codex 独立复核 `a41818a`+`a631c0b` 后以一条具体问题阻塞 R05：默认注册函数只硬编码
`get_player_snapshot` / `get_inventory_snapshot`，没有读取导出的 `defaultCapabilityRegistry`，
因此文档宣称的“源码表追加”会被静默忽略；记录还把无界注册映射写成“有界”。

修复前先加入失败回归（均在 `a631c0b` 上复现失败，修复后通过）：

- `default table registration > registers every entry exported by the default table`：
  向导出表追加条目后，工厂与 router 均应能分发。
- `default table registration > looks up existing default entries ... at dispatch time`：
  单次分发应从导出表解析已有名称，保留旧路径的每次查找语义。

实现改为遍历导出表的当前键注册，并在每次分发时从表中解析处理器；内置 `payload.target`
校验、重名拒绝、显式替换、旧句柄安全注销均保持不变。未改 `manifest.json` / `vectors.json`
/ `protocol.ts`，也未改 `setCapabilityHandler` 的聚合覆盖语义。Python 模块文档字符串已精简，
`register` 的 Raises 区分 `ValueError`（空名称）与 `TypeError`（不可调用处理器）；协议文档
删除未使用的示例导入。运行时向导出表新增“新名称”仍需 `registerCapability`，已有名称的
替换/删除会在下一次分发生效——这是对旧“每次分发查表”行为可保留的部分。

Codex 复核证据：独立重跑 30 个 Python 测试（registry／public API／facade）、ruff、
mypy 37 个源文件、`git diff --check` 与 41 个 addon 测试（capabilityRegistry + router）
全部通过；问题来自静态审查而非测试失败。本次修复后仍由主代理独立复核，不自行宣称通过。
