# ws-sdk 渐进重构执行方案

制定日期：2026 年 10 月 31 日；2026 年 11 月 1 日按冒烟结果与 V2-only 要求修订。基线版本：`0.2.1`；基线提交：`a3034f80cfb57afdbffc485c66a7e2bd6214060e`。

本方案依据[代码评审](../../reviews/2026-10-31-protocol-refactor-proposal.zh.md)与[社区调研](../../reviews/2026-10-31-community-protocol-research.md)。目标是把建议变成可以逐项实施、核查和回退的工作，不在这一轮直接开始修改运行时代码。

## 怎么使用这份方案

- **看整体安排：** 阅读本文。
- **看当前进度与下一步：** 打开[任务清单](tasks.zh.md)。它是任务状态的唯一记录位置。
- **检查一项是否真的完成：** 查看该任务的验收记录，格式使用[验收记录模板](acceptance-template.zh.md)。

最终交付按[任务清单](tasks.zh.md#最终交付要求)与[V2-only 整改方案](v2-only-remediation.zh.md)执行：R18 首次实机冒烟已发现问题，新增 R18A 完成修复、指定依赖升级和 V1 全面清理，再完成 R18 最终复测，R19 收口。当前只更新文档，未获本轮代码实施授权。最终用户文档面向首次接触项目的读者，不保留“尚未发布的当前源码”等提示。

以后可以直接说“执行 R01”或“继续下一项”。执行者先查看任务状态与依赖，完成该项的代码、测试、说明及记录，再报告结果。若说“继续到第二阶段完成”，就在已授权范围内连续推进，不要求逐项重复确认。

每项默认对应一个可独立审查的改动；过大时拆为子任务，并保留原任务编号。原则上一次只推进一个有代码改动的任务，防止协议与调度同时变化后无法定位问题。本文不要求并行派工。

## 已确定的方向

用户已经选择按评审建议逐步重构。下列事项沿用该方向，不再额外请求确认：

| 决定 | 执行方式 |
| --- | --- |
| 项目定位 | 保持 Minecraft Bedrock 通信 SDK；不引入消息代理、模型服务或业务会话管理 |
| WebSocket 实现 | 继续使用现有库，保留目前支持范围；不重写底层握手与帧处理 |
| 协议方向 | 借鉴 JSON-RPC 的交互模型、RSocket 的流式规则与 CloudEvents 的扩展思路；不直接整套引入 |
| 旧协议 | 最终仅 MCBEWS/2；R18A 删除 V1 正向兼容，旧端明确拒绝；旧样本仅作历史与负向测试 |
| 旧接口 | R18A 删除旧公开入口、兼容别名、适配器和生产资产；R18 验证最终包，R19 核对收口 |
| 调度行为 | 最终入口使用可靠调度和强制 V2 准入；旧串行/手动激活路径不能绕过准入 |
| 附加包依赖 | 对齐当前 manifest：server 2.8.0、server-ui 2.1.0；核对 1.26.30 游戏基线与 gametest |
| 示例聊天 | 只响应 ASCII ! 前缀；普通聊天静默，协议帧与通用事件不受过滤 |
| 安全预算 | 保留 461 字节默认命令行预算及“只能降低”的规则；上行按自己的载体限制检查 |
| 玩家隔离 | SDK 管理消息归属、顺序和任务；宿主管理身份授权、历史与业务状态 |
| 日志 | 默认摘要，可配置完整数据包与脱敏；日志不能拖住收发 |
| 文档 | 执行记录使用完整中文；公开源码说明继续遵守仓库的英文要求；发布文档保持中英文配对 |

R00—R17 的兼容设计保留为历史实施记录。2026-11-01 用户明确选择破坏性升级：最终不保留旧公开 API 或 MCBEWS/1 线协议成功路径。MCBE 原生 WS 版本字段不是旧 addon 协议，不能误删。

## 最终要交付什么

1. 开发者可以直接执行游戏命令或请求附加包能力，由 SDK 配对回复和处理超时。
2. 一个慢处理器、慢玩家或慢日志接收器不会阻止其他请求回复被读入。
3. 新增能力只需注册处理函数和数据规则，不修改总入口与分片层。
4. Python 与附加包共用明确的新协议，支持自定义元数据及双向分片。
5. 内容尚未产生完也可以持续发送，支持结束、失败、取消和有界缓冲。
6. V2 正常通信与旧端拒绝均有测试和实机记录；最终生产包没有 V1 业务实现或旧公开入口。
7. 任务、测试结果、协议样本与实机记录能够对应起来。

## 每项任务怎样执行

1. **开始前：** 检查工作区和任务依赖，记录开始时的提交、已有改动与本项范围。
2. **固定预期：** 将验收条件落到测试或操作步骤；修复问题时先验证旧行为能复现。
3. **完成一项可审查的改动：** 不把无关格式化、依赖升级或协议调整混在一起。
4. **验证：** 执行本项测试和影响范围内的回归；阶段结束再跑完整门槛。
5. **留证：** 记录命令、环境、结果、改动文件及未覆盖项；更新唯一任务表。
6. **报告：** 说明完成了什么、证据在哪、尚存限制和下一任务。

任务状态只有五种：**未开始、进行中、待验收、已完成、受阻**。代码写完但实机未测，应是“待验收”；不能标“已完成”。可选能力通过评估决定不做，必须记录理由，对应评估任务仍需要验收。

验收条件用“任务编号＋序号”引用，例如 R03-2。若新增条件，追加编号，不把已有编号挪给别的条件。测试文件可以调整名称，验收编号与实际测试的对应关系留在记录中。

## 共用的完成标准

一项任务只有同时满足以下要求才算完成：

- 本任务所有必需验收条件通过，并能找到测试名称或人工记录。
- 没有新增失败；如基线已有失败，必须保留证据并确认不是本项引入，不得掩盖。
- 新增任务、队列、等待表、缓存都有容量或生命周期约束。
- 新公开行为有说明；兼容行为有测试，不靠代码注释代替。
- 文档中的能力与实现一致，尚未支持的部分明确写出。
- 验收记录填写完整，任务表包含结果、证据路径及提交或改动标识。

问题修复测试先失败再通过；仍保留的行为继续回归。被 V2-only 决定覆盖的旧成功兼容测试改为明确拒绝测试，不能无替代地删除。不要用大量与实现逐行对应的测试替代可观察行为测试。

### 并发与性能怎样验收

并发正确性优先使用可控事件与模拟时钟。例如暂停玩家甲的处理器，再确认玩家乙和命令回复都能完成；不以“等待几十毫秒后大概没堵住”作为唯一证据。

容量测试使用刻意调小的配置验证边界，不擅自把测试用的小值设成生产默认值。发送限速、重组上限和超时沿用现有默认值；新增配置值根据基线实验选定，并在改动记录中解释。

性能验证使用相同环境、负载、运行次数和内容比较前后结果，至少记录中位数、95 分位延迟、命令数量和内存峰值。若变化超过基线重复运行的波动范围，必须分析原因；不能在没有测量时承诺更快，也不能在结果出来后修改门槛掩盖退化。

当前覆盖率门槛为 85%，不降低它。发布前继续验证 Python 3.11—3.14 与 websockets 12、14、16 的现有矩阵；未在本机覆盖的组合由持续集成给证据，不写成“本机全部通过”。

上一轮评审中，八个相关测试文件的 100 项测试通过，另有 9 条已有弃用警告。这是历史证据，不能代替 R00 的全量基线或本轮实施后的测试。

## 协议切换与回退

2026-11-01 决定覆盖原“冻结 V1 并兼容回退”的最终要求。历史记录和拒绝测试可保留旧样本，生产运行和分发资产不保留旧实现。

新服务必须先完成 V2 应用层协商，再开放业务和发送连接成功提示。明确旧端立即拒绝；无回复或无 addon 限时关闭；不能通过保留旧 facade 或配置开关绕过准入。
新 addon 不执行旧服务的 V1 请求；它没有 WS 关闭句柄时只承诺拒绝业务。具体状态机和关闭边界见[整改方案](v2-only-remediation.zh.md)。

回退通过有针对性的反向提交或整套配套部署版本回退，不重置工作区、不撤销他人修改。必须断开并建立新会话，不在同一连接换协议，也不自动重放副作用命令。
新版内部不存在“协商失败就选旧版”的回退路径。

## 哪些情况需要用户决定

**当前没有阻止文档规划的待确认项。** 用户已明确最终 V2-only 与指定依赖，当前只授权修改文档。代码实施按后续指令推进。只有出现以下实际分歧时才请求决定，并先准备好影响范围与替代方案：

| 触发情况 | 需要确认的决定 | 在此之前仍可做的工作 |
| --- | --- | --- |
| 所需性能必须以明显更高内存、更大依赖或持久化状态换取 | 选择哪一种成本 | 提供实测对比与简化方案 |
| 实机验收无法访问游戏环境 | 可用游戏版本、平台及由谁操作实机 | 完成自动化测试、操作脚本和记录模板 |
| 准备切换发布默认值或实际对外发布 | 发布版本与切换时点；发布操作按当时授权执行 | 做好候选包、迁移文档、完整验收与发布说明 |

不会为文件命名、内部类拆分、普通测试写法等实现细节反复询问。实机环境的信息到 R18 前准备即可，不必为它阻塞第一阶段。
