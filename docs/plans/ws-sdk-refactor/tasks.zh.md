- [x] R01-2：暂停一个业务处理器时，另一玩家与已登记请求的回复仍能完成；每条连接只有一个底层读取任务。

### R02：统一请求等待与回复配对

**范围：** `addon/service.py`、`addon/session.py`、`delivery/outbound.py`、命令回复入口、附加包示例的命令等待逻辑。

**交付物：** 共用请求生命周期实现；可等待的原生命令入口；附加包请求复用同一机制；示例删除重复等待表。

- [x] R02-1：发送前完成登记；模拟“发送时立即回包”也能正确完成，不丢失早到回复。
- [x] R02-2：原生命令与附加包处理结果分别配对；脚本事件发送确认不能提前结束附加包请求。
- [x] R02-3：相同编号在不同连接、不同请求类别或发起方向互不干扰；重复、未知、迟到回复不恢复已结束请求。
- [x] R02-4：成功、远端失败、发送失败、编码失败、超时、取消、断连后等待表均无残留，最终状态只确定一次。
- [x] R02-5：旧发送接口仍返回原本约定的值，旧回调仍按合同收到事件；新示例无需宿主自行维护等待表。

**范围：** 新连接运行路径的所有发送出口，包括握手、订阅、原生命令、文字、脚本事件和附加包消息。

**交付物：** 每连接统一发送入口；消息数量与字节容量限制；公平调度；可观察的发送结果。

- [x] R03-1：新路径所有发送都经过同一调度器；底层传输仅由该调度器调用；握手与必要订阅先于业务发送。
- [x] R03-2：限速按连接总量执行，并使用模拟时钟验证；不能多开一个发送任务就绕过限制。
- [x] R03-3：队列满时关键请求、回复和结束信号不静默丢弃；受控等待或明确失败，关闭时等待者全部释放。
- [x] R03-4：长传输期间控制消息和短回复仍有发送机会；同一逻辑消息内部顺序符合协议。
- [x] R03-5：最终命令行符合当前预算；超长原生命令明确失败；发送失败传播给所属请求，单条连接故障不波及其他连接。

**边界：** 不在读取任务内等待业务发送完成。为必要控制消息预留受限容量；资源完全耗尽时有明确关闭或错误策略，不创建无限补救队列。旧入口的旧溢出策略在兼容层保留并说明。
