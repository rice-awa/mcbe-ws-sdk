## 第一阶段：收发可靠

### R01：接收循环与业务任务分离

**范围：** `gateway/server_facade.py`、`gateway/connection.py`、`gateway/events.py`、`gateway/hook.py`、界面消息回调路径。

**交付物：** 显式启用的新调度入口；按连接管理的业务任务；有界业务队列；回调执行顺序说明。

- [x] R01-1：新路径下，玩家、界面消息和连接建立回调均可等待附加包回复；读取任务仍持续处理回包。
- [x] R01-2：暂停一个业务处理器时，另一玩家与已登记请求的回复仍能完成；每条连接只有一个底层读取任务。
- [x] R01-3：业务队列已满时读取任务不等待它腾空；新业务得到明确拒绝或记录过载，已有请求回复照常配对。
- [x] R01-4：SDK 持有并回收所有业务任务；断连后任务被取消并等待退出，无未读取异常；观察者不阻塞读取。
- [x] R01-5：旧入口行为测试保持通过；新行为有明确启用方式；R00 的阻塞回归用例在新路径正常通过。

**边界：** 不改线格式。使用异步等待不会自动解决 CPU 密集同步代码阻塞，文档明确这类工作应由宿主移出事件循环。

### R02：统一请求等待与回复配对

**范围：** `addon/service.py`、`addon/session.py`、`delivery/outbound.py`、命令回复入口、附加包示例的命令等待逻辑。

**交付物：** 共用请求生命周期实现；可等待的原生命令入口；附加包请求复用同一机制；示例删除重复等待表。

- [x] R02-1：发送前完成登记；模拟“发送时立即回包”也能正确完成，不丢失早到回复。
- [x] R02-2：原生命令与附加包处理结果分别配对；脚本事件发送确认不能提前结束附加包请求。
- [x] R02-3：相同编号在不同连接、不同请求类别或发起方向互不干扰；重复、未知、迟到回复不恢复已结束请求。
- [x] R02-4：成功、远端失败、发送失败、编码失败、超时、取消、断连后等待表均无残留，最终状态只确定一次。
- [x] R02-5：旧发送接口仍返回原本约定的值，旧回调仍按合同收到事件；新示例无需宿主自行维护等待表。

**边界：** 复用管理机制，不合并不同“成功”的含义。超时包含排队还是仅包含远端等待，必须写成公开约定。

### R03：统一发送调度与过载处理

**范围：** 新连接运行路径的所有发送出口，包括握手、订阅、原生命令、文字、脚本事件和附加包消息。

**交付物：** 每连接统一发送入口；消息数量与字节容量限制；公平调度；可观察的发送结果。

- [x] R03-1：新路径所有发送都经过同一调度器；底层传输仅由该调度器调用；握手与必要订阅先于业务发送。
- [x] R03-2：限速按连接总量执行，并使用模拟时钟验证；不能多开一个发送任务就绕过限制。
- [x] R03-3：队列满时关键请求、回复和结束信号不静默丢弃；受控等待或明确失败，关闭时等待者全部释放。
- [x] R03-4：长传输期间控制消息和短回复仍有发送机会；同一逻辑消息内部顺序符合协议。
- [x] R03-5：最终命令行符合当前预算；超长原生命令明确失败；发送失败传播给所属请求，单条连接故障不波及其他连接。

**边界：** 不在读取任务内等待业务发送完成。为必要控制消息预留受限容量；资源完全耗尽时有明确关闭或错误策略，不创建无限补救队列。旧入口的旧溢出策略在兼容层保留并说明。

### R04：收紧隔离、关闭与残留清理

**范围：** 新运行路径的连接、玩家任务、请求、发送队列和重组缓冲；附加包现有串行调度的容量与资源分组。

**交付物：** 生命周期状态与关闭流程；按连接和玩家分组；世界修改操作的明确顺序规则。

- [x] R04-1：同玩家连续操作按约定保持顺序，不同玩家可并发；无玩家身份的控制消息不会错误归入某个玩家队列。
- [x] R04-2：需要顺序修改同一世界资源的操作仍串行；只读或独立操作可以按注册规则并发。
- [x] R04-3：关闭与发送、超时、回包同时发生时，连接只清理一次；关闭后的新发送明确报错。
- [x] R04-4：反复建立和关闭连接后，SDK 管理的任务、等待表、队列和缓冲回到初始数量；旧连接回包不进入新连接。
- [x] R04-5：附加包就绪前后都有待处理上限；慢处理器不会形成无限 Promise 链，超载结果可观察。

**阶段门槛：** R01—R04 全部通过，Python 全量检查及相关附加包检查通过，查询背包的模拟完整链路无需宿主自行创建请求任务。

- [ ] R12-4：同一 traceId 可串起多个不同请求；调用方不能覆盖保留协议字段或伪造已认证身份。

**边界：** 业务处理器跨相同顺序组反向调用可能造成互相等待，须明确重入策略或显式拒绝，不能单靠增加任务数量规避。

### R13：版本协商与兼容回退

**范围：** 连接就绪、附加包探测、协议选择、兼容适配。

**交付物：** 有界探测与协商；连接级能力集合；旧版和无附加包行为说明。

- [ ] R13-1：新服务端＋新附加包协商后使用新协议；新服务端＋旧附加包只使用双方支持的旧能力。
- [ ] R13-2：旧服务端＋新附加包仍支持旧格式；无附加包时普通聊天与原生命令不被无限探测阻塞。
- [ ] R13-3：不支持的版本或能力明确失败；指定必需元数据或流式时，不悄悄降级为丢字段的旧请求。
- [ ] R13-4：探测次数、时间与缓冲有上限；普通消息不误识别为握手；不在未完成消息中途切换协议。
- [ ] R13-5：重连重新建立会话并协商，旧流和请求不复活，也不自动重放世界修改命令。

**阶段门槛：** 旧协议样本不变；新协议交叉测试、元数据往返、双向大消息与兼容组合的自动化测试全部通过。实机组合仍列为 R18 的独立门槛。

## 第四阶段：真正流式

### R14：持续流式数据与正常结束

**范围：** 连接高层入口、新协议协商能力、双端持续数据处理。

**交付物：** 持续生产与消费入口；流标识和逻辑序号；正常结束；首段到达时间测量。

- [ ] R14-1：生产者尚未产生最后一项时，消费者已收到第一项；开始发送不需要总长度。
- [ ] R14-2：同一连接可并行处理普通请求和多条流，流之间不串数据；两端可同时生产和消费。
- [ ] R14-3：一项流数据过大时通过 R11 分片，重组后只作为一项交付；流序号与片段序号不混用。
- [ ] R14-4：空流、正常流和大项流均有且只有一次完成信号；顺序错误和缺项有明确处理。

**边界：** 先提供有界缓冲与过载终止，不把固定发送间隔称为接收方背压。

### R15：流式取消、异常与慢端处理

**范围：** 双端流状态、生产任务、缓冲、关闭与错误传播。

**交付物：** 取消与失败终止；慢消费者策略；不完整流清理。

- [ ] R15-1：发送方失败、接收方取消、断连、超时与正常结束竞争时，只形成一个终止结果。
- [ ] R15-2：终止后不再交付新数据，迟到片段不重新创建已结束流，生产任务和缓冲被释放。
- [ ] R15-3：消费者暂停后缓冲不超过数量与字节上限；按合同暂停生产或明确结束，不无限积压。
- [ ] R15-4：一条流被取消不会取消同连接其他请求；已经执行的世界修改不会被错误宣称已撤销。
- [ ] R15-5：不支持流式的旧端收到调用时明确报能力不支持，不退化成假流式。

### R16：评估并按需实现接收额度

**范围：** R14—R15 的慢端实测与协议能力扩展。

**交付物：** 一份有测量依据的决定；需要时增加可协商的接收额度，否则明确当前策略的能力边界。

- [ ] R16-1：比较持续流、突发大项与暂停消费者三类负载，记录缓冲峰值、完成时间、终止次数与额外命令数。
- [ ] R16-2：若既定有界策略满足需求，记录不引入额度的原因；若不能在持续接收场景中保持有界且不中断，则实现并协商额度机制。
- [ ] R16-3：若实现，零额度时不发送数据；一项拆成多片只扣一次额度，仍受字节上限保护。
- [ ] R16-4：若实现，重复、非法、溢出额度和取消竞争有测试；对不支持额度的对端仍有明确有界策略。

**阶段门槛：** 流式完整生命周期通过测试；R16 的实现或不实现均有证据，不能把“尚未评估”当作“不需要”。
