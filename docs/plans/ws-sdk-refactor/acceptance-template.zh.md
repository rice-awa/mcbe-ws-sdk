# 单项任务验收记录模板

执行一项任务时，将本模板复制到本目录下的 `records/Rxx.zh.md`；该路径是未来执行时创建的记录，不代表现在已有结果。完成后把真实记录链接写入[任务表](tasks.zh.md)。

## 基本信息

| 项目 | 记录 |
| --- | --- |
| 任务编号与名称 | 填写任务表中的编号与名称 |
| 执行日期／执行者 | 填写实际信息 |
| 开始基线 | 提交编号，及开始时已有的未提交改动 |
| 改动标识 | 提交编号；未提交时列出明确文件与差异摘要，不虚构提交 |
| 前置任务 | 编号、状态与证据链接 |
| 本项状态 | 进行中／待验收／已完成／受阻 |

## 这次改变了什么

说明原问题、现在的行为和使用者如何感知；列出主要文件及职责变化。描述范围外的遗留问题，避免把局部修复写成全项目完成。

## 验收逐项对照

| 验收编号 | 测试节点或操作步骤 | 预期结果 | 实际结果 | 证据位置 |
| --- | --- | --- | --- | --- |
| Rxx-1 | 填写实际测试或手工步骤 | 填写可观察结果 | 通过／失败／未验证 | 日志、测试节点或记录 |

每个必需条件都要有一行，不能用一句“测试通过”代替。已跳过的测试、预期失败和未执行项分别说明。

## 命令与环境

| 运行位置 | 实际命令／步骤 | 环境与版本 | 退出码及结果 |
| --- | --- | --- | --- |
| 填写目录 | 填写实际执行内容 | Python／Node.js／依赖版本等 | 通过数、失败数、警告与耗时 |

只记录已经运行的命令。缺少依赖或环境导致无法执行时，写明原因和补验方法。原始日志不包含密钥或私人业务内容。

## 兼容性与资源检查

| 检查项 | 结果与依据 |
| --- | --- |
| 旧导入、参数、返回值和回调顺序 | 通过／不涉及／有变化，附依据 |
| 旧协议清单与样本 | 是否变化，原因 |
| 并发与顺序 | 如何验证不串包、不堵塞 |
| 队列、任务、等待表与缓冲 | 上限与清理证据；不涉及则注明 |
| 依赖与配置默认值 | 是否改变，依据是什么 |
| 日志与公开文档 | 行为是否同步说明 |

## 实机或性能记录（需要时填写）

记录游戏版本、平台、Beta APIs 状态、双方软件版本、样本内容、运行次数和统计方式。比较前后使用相同条件，列出中位数、95 分位延迟、包数与内存；无实测则写“未验证”。

## 剩余问题与回退

列出剩余问题、影响任务、负责人或处理方式、解除条件；说明本项如何单独关闭或反向修改。不以“回滚整个仓库”作为回退方案。

## 验收结论

填写“通过”“部分通过，待补验”或“不通过”，说明原因。只有全部必需条件通过才能将任务表改为“已完成”。最后写出下一项可执行任务及其前提。
