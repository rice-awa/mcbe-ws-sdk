# ws-sdk 协议与架构重构建议

评审日期：2026 年 10 月 31 日。

代码基线：`a3034f80cfb57afdbffc485c66a7e2bd6214060e`，项目版本为 `0.2.1`。本文是设计评审与重构建议，不代表这些能力已经实现。

文中的“宿主”指使用 SDK 的上层程序，“附加包”指游戏端的 addon。“路由”就是按功能名称选择处理函数，“元数据”就是说明消息背景的附加信息。正文先讲问题与取舍，文件和代码标识只用于核对依据。

## 先说结论

你的方向是对的：这个项目适合以消息为中心，提供请求、回复、事件和流式传输，不适合硬套 RESTful。

但当前最值得改的，并不是把字段名字缩短，也不是再加一层抽象。主要问题有三个：

1. **接入者要理解太多内部运行规则。** 例如，在消息回调里直接等待附加包回复，就会堵住处理回复的接收循环；原生命令的请求配对也要由宿主自己实现。
2. **通用通信与具体产品功能混在协议里。** 玩家聊天、会话管理、审批、文本角色、用量统计分别有专用格式，增加一种功能往往会牵动多处代码。
3. **已有分片能力，还没有完整的流式通信能力。** 长文本拆开发送、持续产生新内容、接收方主动要求减速，是三个不同问题。

建议保留现有的 WebSocket 库、字节预算保护、连接隔离、异常类型、协议清单和跨语言测试；重构收发调度、请求关联、业务路由与扩展字段。最后再引入新版本的附加包协议。

期望的结果是：开发者接入一个新能力，只需注册处理函数和定义数据，不需要修改 SDK 的总入口、消息分类器和分片实现。

## 一、先明确项目负责什么

### 1. 它是 Minecraft 通信 SDK

建议把定位收敛为：**面向 Minecraft Bedrock 的双向通信 SDK，隐藏连接管理、命令配对、附加包桥接、分片重组和发送调度。**

WebSocket 的握手、心跳、关闭和底层帧处理继续交给 `websockets`。本项目应可靠地使用并暴露必要配置，无须自己重写这些机制。库的并发收发模型已经支持独立发送与接收，但应用层仍必须正确组织任务，不能让业务等待阻止读取回复。[外部依据：Python websockets 官方并发示例与设计文档](https://github.com/python-websockets/websockets/blob/16.0/docs/howto/patterns.md)。

还有一处命名容易误解：Python 程序是 WebSocket 服务端，Minecraft 游戏是连接它的客户端；但一次请求既可以由 Python 发起，也可以由附加包发起。“谁建立连接”和“谁发起请求”应分开描述。新接口应允许两端注册功能并发起调用，同时处理各自收到的请求。

“完整支持”也要有范围清单。目前网关默认订阅并专门解析的是玩家消息，不能据此称为已经完整覆盖所有 Minecraft 事件。建议提供按事件名称订阅、取消订阅和接收原始事件的通用入口，再为常用事件提供类型化支持；不同游戏版本支持哪些事件，需要明确记录和验证。代码依据：[当前订阅与解析入口](../../src/mcbe_ws_sdk/gateway/handler.py)第 81—110 行。

### 2. 保留游戏的外层协议，统一自己控制的内层协议

实际通信路径可以画成：

```text
Python 程序
  ├─ 原生命令、显示文字 ─→ Minecraft 命令请求 ─→ 游戏执行
  │                                            └─ 命令结果返回
  └─ 附加包消息 ─→ scriptevent ─→ 附加包处理 ─→ 假人聊天 ─→ Python 程序

玩家普通聊天 ─→ Minecraft 事件 ─→ Python 程序
```

原生命令、显示文字、调用 Script API 可以共用发送调度，但完成条件不同：命令结果表示游戏执行了命令；附加包回复才表示附加包处理完成。收到“脚本事件已发送”不能当成某项能力已经执行成功。

也不要让普通聊天强行带上附加包消息头。普通玩家消息只需要在 SDK 内部转成统一的事件对象。

## 二、当前代码有哪些值得保留的基础

| 现有基础 | 保留原因 | 代码位置 |
| --- | --- | --- |
| 按连接保存队列、请求和重组缓冲 | 已经具备一对多隔离的基本形状 | `gateway/connection.py`、`addon/session.py` |
| UTF-8 字节预算检查 | 中文、表情、转义字符不能按字符数量估算 | `flow/flow_control.py` |
| 原生命令超长时直接报错 | 不能把一条游戏命令切成几条后假装仍是同一操作 | `chunk_raw_command()` |
| 重组数量、大小、过期时间限制 | 避免不完整消息长期占用内存 | `AddonBridgeSession`、`responseSync.ts` |
| 宿主通过接口注入行为 | SDK 不必依赖上层应用的模型和服务 | `gateway/hook.py`、`gateway/sink.py` |
| 同一份协议清单与测试样本 | 有助于约束 Python 和 TypeScript 的一致性 | `manifest.json`、`vectors.json` |
| 事件监听器异常隔离 | 一个监听器出错不会阻止后续监听器 | `gateway/events.py` |

仓库旧评审描述的是更早版本，不能直接照抄其中的问题清单。例如，当前事件总线已经隔离单个监听器异常，部分配置也已经做成只读。本文以这次读取的源码为准。

## 三、真正需要重构的地方

### 1. 接收循环承担了业务等待

当前入口逐条读取消息，并等待消息处理完成；玩家回调、连接建立回调和事件监听器都可能在这个路径上被等待。

如果玩家发来“查询背包”，回调向附加包请求数据，然后直接等待回复，会发生：

```text
接收循环调用玩家回调
  → 回调发出背包查询
  → 回调等待附加包回复
  → 回复已经到达，接收循环却仍在等待回调结束
  → 查询超时后，接收循环才读到回复
```

这次用模拟连接复现了该行为，并做了对照：让回调把工作交给单独、可回收的任务后，回复在超时之前正常完成。

这不是所有调用都会失败，也不是此前无人知道的问题。仓库的附加包示例已经明确要求另建任务来避免阻塞。问题在于，这个要求泄露给了每个接入者。

**建议：由 SDK 管理业务任务，接收循环优先完成解析、请求配对和轻量分发，不等待业务结果。** 队列满时也不能停在等待业务队列腾空上，否则后面的回复仍然读不到。应拒绝新业务、报告过载，或按明确定义的策略处理。

代码依据：[接收入口](../../src/mcbe_ws_sdk/gateway/server_facade.py)第 188—211、363—368 行；[附加包示例说明](../../examples/addon-server/README.zh.md)第 139—149 行。

### 2. 请求配对职责不统一

附加包请求由 SDK 登记、等待和清理；原生命令请求却只返回请求编号，把命令回复交给宿主自行配对。

这会让每个宿主重复写等待表、超时处理、断连清理、迟到回复处理。仓库示例里的命令执行器已经说明，这是一块真实存在的公共需求。

**建议：统一请求生命周期，但保留两种回复的不同含义。** 原生命令等待游戏的命令结果；附加包请求等待附加包的处理结果。两者可以复用内部等待表机制，不能混用同一个“成功”判断。

代码依据：[原生命令发送](../../src/mcbe_ws_sdk/delivery/outbound.py)第 66—81 行；[命令回复转交宿主](../../src/mcbe_ws_sdk/gateway/server_facade.py)第 275—295 行；[附加包请求](../../src/mcbe_ws_sdk/addon/service.py)第 93—177 行。

### 3. 业务种类决定了传输格式

当前协议分别认识能力请求、聊天分片、会话请求、会话回复、审批决定和文本回复。文本回复还包含用户、助手、审批等角色以及用量统计。

这些功能可以存在，但通用通信核心不应该必须理解它们。否则下一次加入交易确认、任务进度或地图同步，又要增加一套专用分类、字段、编码与回调。

**建议：把会话、审批、聊天显示做成可选扩展。核心只认识请求、回复、通知，以及后续增加的流式消息。** 功能名称由路由注册表决定，功能数据由各扩展自行验证。

旧版本仍按现有格式工作；新核心可通过兼容适配器承接旧功能，不应静默改掉旧协议。

代码依据：[现有通道与角色](../../src/mcbe_ws_sdk/profiles/mcbews_v1/manifest.json)；[控制消息分类](../../src/mcbe_ws_sdk/profiles/mcbews_v1/classifier.py)；[业务数据模型](../../src/mcbe_ws_sdk/profiles/mcbews_v1/models.py)。

### 4. 允许附加字段，不等于真正可扩展

当前并非完全不能扩展：能力名称是字符串，业务数据是字典，附加包也允许注入处理函数。

但扩展没有贯穿整个链路：

- Python 请求接口没有单独的元数据入口。
- 附加包解析请求时重新构造固定字段对象，额外的顶层字段不会进入处理上下文。
- 附加包注入的是一个总处理函数，会整体替换默认能力表；新增一个能力不能自然地与内置能力组合。
- 一部分模型允许附加字段，另一部分拒绝附加字段，缺少统一规则。

**建议：核心字段严格验证，另设明确的元数据区；处理器按功能名称逐项注册。** 未知的可选元数据应被保留，未知的功能名称则明确返回“不支持”，不能装作处理成功。

代码依据：[请求模型](../../src/mcbe_ws_sdk/profiles/mcbews_v1/models.py)第 35—43 行；[附加包解析与分发](../../addon/scripts/bridge/router.ts)第 132—173、239—240、274—318 行；[默认能力表](../../addon/scripts/bridge/capabilities/index.ts)。

### 5. 分片重组没有覆盖双向的所有消息

上行的能力回复、界面聊天已经可以分片；下行能力请求却直接编码成一条 `scriptevent`。当前附加包解析器也要求这一条内容就是完整 JSON。

不能简单调用普通的脚本事件拆分函数解决：把 JSON 切成数段，并不会让附加包自动知道如何拼回去。下行必须有明确的片段标识和重组过程。

本次还做了一个大小检查：使用当前生成方式的请求编号、`get_inventory_snapshot` 功能名，以及包含玩家名和文本的对象，空文本时命令占 168 字节；加入 300 个 ASCII 字符后占 468 字节，超过 461 字节预算，正确地被拒绝。这只是这一组字段的测量，不是所有消息的固定开销。

**建议：新版本让完整的逻辑消息共用双向分片层；原生游戏命令仍不能随意切割。**

注意，461 字节是项目记录的经验性命令行预算，不是 WebSocket 标准限制；上行目前还有按 Unicode 码点计算的单片内容限制，两者不能混为一谈。

代码依据：[能力请求编码](../../src/mcbe_ws_sdk/profiles/mcbews_v1/codec.py)第 48—63 行；[普通脚本事件拆分](../../src/mcbe_ws_sdk/flow/flow_control.py)第 78—110 行；[协议限制](../../src/mcbe_ws_sdk/profiles/mcbews_v1/manifest.json)。

### 6. 分片发送还不是持续流式传输

当前文本发送接口接收完整字符串，生成一个完整分片列表，每片包含“第几片／共几片”。附加包收齐后才返回完整文本。

可以把区别理解成：

| 能力 | 含义 | 例子 |
| --- | --- | --- |
| 分片 | 内容已经完整，只是一次装不下 | 把背包快照分成五段 |
| 流式 | 内容还在产生，先发送已经产生的部分 | 一边生成回复，一边展示 |
| 背压 | 接收方让发送方适当减速 | 界面只来得及处理十条，生产者先暂停 |

真正的流式传输不能要求开始时知道总片数；还要定义顺序、正常结束、出错结束和取消。流里某一条数据过大时，仍然可以继续使用下层分片，但两种序号应分开。

代码依据：[完整文本发送](../../src/mcbe_ws_sdk/profiles/mcbews_v1/delivery.py)第 29—58 行；[预先计算分片](../../src/mcbe_ws_sdk/flow/flow_control.py)第 131—191 行；[收齐后返回](../../addon/scripts/bridge/responseSync.ts)第 183—260 行。

### 7. 队列、限速和日志还没有统一收口

当前发送队列有上限，但满时丢弃最旧消息。这对可以覆盖的状态提示或许合适，对请求回复、流式片段、结束通知则可能破坏完整性。

同时，并非所有发送都经过这个队列；直接发送命令和附加包请求可以走其他路径。每次批量发送各自等待固定间隔，不能自动保证整个连接的合计发送速率。附加包端也存在串行执行链：一个慢操作会拖住后续操作，就绪后的执行链没有显式的待处理数量上限。

日志方面已经有原始收发事件和可选原始发送日志，基础不错，但发送、接收、业务日志仍分散在不同位置。

**建议：所有出站路径经过同一个连接级发送调度；业务消息和日志观察各有容量与失败策略。** 日志写入慢不能堵住网络读取。日志可以丢采样，关键回复不能静默丢弃。

代码依据：[丢弃最旧项](../../src/mcbe_ws_sdk/gateway/connection.py)第 47—68 行；[发送与逐批等待](../../src/mcbe_ws_sdk/delivery/outbound.py)第 103—160 行；[附加包串行调度](../../addon/scripts/bridge/router.ts)第 67—76、180—185 行；[原始收发事件](../../src/mcbe_ws_sdk/gateway/server_facade.py)第 233、436—460 行。

## 四、社区方案中，哪些值得借鉴

通过 GitHub CLI 搜索并阅读固定提交的源码后，最值得组合借鉴的是以下几组。这里是在选择设计经验，不是在建议同时安装这些框架。

| 参考 | 借鉴什么 | 对本项目的取舍 |
| --- | --- | --- |
| JSON-RPC、VSCode JSON RPC | 请求与回复配对；通知；处理函数注册；连接关闭时结束等待 | 最适合作为基础交互模型，但流式和分片需要另行约定 |
| RSocket | 持续数据流、结束、取消、接收额度；区分流与分片 | 学状态规则，不把完整二进制协议硬塞进聊天通道 |
| CloudEvents | 固定核心字段与可扩展上下文；追踪信息 | 借鉴扩展规则，不要求每条小消息套上完整事件格式 |
| mcwss、bedrockpy | 简单的游戏命令调用与事件订阅体验 | 不能照搬其连接与玩家关系；bedrockpy 已归档 |
| WAMP | 能力协商、注册、分阶段返回 | 可作为功能增长后的参考，现阶段无需引入完整路由器 |

依据分别为[微软的连接实现](https://github.com/microsoft/vscode-languageserver-node/blob/a0981e3d9c68397553696b0fb2bebb9dd024e4ba/jsonrpc/src/common/connection.ts)、[RSocket 协议](https://github.com/rsocket/rsocket/blob/0f6e5554a5f9abbb1c6c7ec2138d2f3e0ab280e8/Protocol.md)、[CloudEvents 规范](https://github.com/cloudevents/spec/blob/102551014f04c3ff2171eca5f6f918975fb500f7/cloudevents/spec.md)、[mcwss 连接实现](https://github.com/Sandertv/mcwss/blob/0244b379697bf0021212c2587d6234eba26aef48/player.go)、[bedrockpy 仓库](https://github.com/bedrock-ws/bedrockpy)、[WAMP 分阶段返回规则](https://github.com/wamp-proto/wamp-proto/blob/76fc32ca6d7f5f397927ff9d0fd0999df1fae9d6/rfc/text/advanced/rpc_progressive_call_results.md)。

本次没有找到经过核查就能确认全面优于当前项目、又覆盖所有需求的现成替代品。这不意味着不存在，只意味着更可靠的选择是有针对性地借鉴。详细判断和实际搜索命令见[社区调研记录](2026-10-31-community-protocol-research.md)。

## 五、建议的架构：少数几个完整职责

不建议先画十几层目录，再给每层套一个接口。应围绕真正需要统一管理的职责组织内部实现，对使用者只暴露少量入口。

```text
宿主应用与可选扩展
      │
      ▼
连接对象：执行命令、发送消息、请求能力、订阅事件
      │
      ├─ 请求关联：配对回复、超时、取消、断连清理
      ├─ 业务分发：按功能和玩家安排可管理的任务
      ├─ 协议编解码：识别原生包、附加包消息与版本
      ├─ 分片重组：按实际载体预算拆分和还原完整消息
      └─ 连接运行：读取、发送排队、速率限制、生命周期
                 │
                 ▼
             Minecraft
```

这些是职责，不要求机械地对应五个公共类。比如请求关联和任务调度可以由同一个连接对象在内部组合，使用者不必手动组装。

### 接收与发送如何互不拖累

每个连接只有一个底层读取任务，确保消息顺序和唯一入口。它先处理回复配对与控制消息，再把业务工作交给受管理的执行队列。业务队列按玩家或明确的资源键保持顺序，不同玩家可以并发；需要顺序修改世界状态的操作仍应串行。

每个连接有一个发送调度入口，统一计算大小、排队、限速和发送结果。控制消息、短回复和大块数据应有公平调度，不能让一个长传输占住整个连接。

任务、等待中的请求和未完成分片都归连接所有。断连时统一结束，后续发送明确报错；重连建立新会话，不自动重放可能有副作用的游戏命令。

### 玩家隔离负责到哪里

SDK 可以提供“连接标识＋玩家标识”的上下文和任务分组，解决消息归属、顺序与清理。宿主继续负责聊天历史、账户权限、业务会话和其他领域状态。

如果事件只有玩家名称，就如实使用这个来源并说明限制，不把名称当成跨重连、跨世界的永久身份。

### 事件订阅与拦截如何分工

- 事件订阅用于得知事情已经发生：例如连接建立、玩家发言、发送失败。
- 拦截器用于决定是否继续处理，以及在允许范围内修改消息。
- 两者应有明确顺序和异常策略；旁路观察者不能无限期占用收发路径。
- 现有回调接口可以作为兼容入口映射到新流程，避免同时保留两套业务分发逻辑。

这里的“改名”不重要，重要的是使用者能知道回调何时执行、能否等待请求、能否阻止继续处理、出错会影响谁。

## 六、建议的新协议形状

### 1. 使用统一消息封套，但不要重复堆字段

“消息封套”就是每条消息外面的一小层说明：它是什么、属于哪次请求、应交给谁处理。里面的正文由具体功能自己定义。

第一阶段只需要三种消息：请求、回复、通知。持续数据流和取消可以在后续阶段增加。下面描述的是设计草案，具体字段拼写应在双方测试样本确定后固定。

| 信息 | 什么时候需要 | 建议规则 |
| --- | --- | --- |
| 协议版本 | 连接协商或消息识别时 | 决定解码规则，不与业务版本混用 |
| 消息种类 | 每条逻辑消息 | 请求、回复或通知 |
| 功能名称 | 请求和通知 | 按名称注册，采用命名空间避免冲突 |
| 请求编号 | 需要回复时 | 回复沿用请求编号，只在所属连接与发起方向内关联 |
| 元数据 | 调用方需要附加信息时 | 用于追踪、业务上下文等，有大小限制 |
| 正文 | 功能需要数据时 | 由该功能验证，可以是明确允许的 JSON 值 |
| 错误信息 | 处理失败时 | 至少包含稳定错误码与可读说明，与成功结果互斥 |

不要求每条通知都携带请求编号。传输层若需要给一个大消息分片，可以生成独立的重组编号，业务处理器不需要操心。

同一请求的回复可以共用请求编号，但一条流中的不同逻辑消息不能仅靠请求编号重组；片段还需要所属消息的编号或流序号。编号不得跨连接或跨重连会话错误关联。

### 2. 请求编号与 traceId 各司其职

请求编号回答：“这份回复对应哪次调用？”

traceId 回答：“这几个调用是否属于同一条完整操作链？”

例如玩家查询背包后又查询位置，这是两个请求，但可以属于同一次用户操作。traceId 放在元数据中可选传递；分片时不必反复携带整套追踪和业务信息。追踪格式可借鉴 W3C Trace Context，初期不必强制依赖完整的 OpenTelemetry。

### 3. 元数据应该怎样扩展

建议明确保留一个元数据对象，约定核心保留键和扩展键的命名方式。扩展字段由发送接口接收，经编码、传输、解码进入处理上下文，并按规则传递到回复和日志。

“支持扩展”的验收应是：一个 SDK 不认识的可选键，经过 Python 到 TypeScript、再返回 Python 后，仍然保持预期的值与类型。仅仅把 Python 模型设为允许额外字段，不算完成。

业务正文里的新增字段由对应功能解释；影响协议语义的新能力则要显式协商，不能把必须理解的要求藏在一个可忽略字段里。元数据中的玩家名或权限声明也不能自动成为可信身份。

### 4. 路由注册应该怎样使用

开发者新增“查询附近实体”时，应只需：

1. 在附加包中注册一个功能名称及其处理函数。
2. 定义并验证这个功能的输入和输出。
3. 在 Python 端按同一名称发起请求。

内置能力作为默认注册项存在。自定义能力与它们并存；重名默认报错，确实要替换时显式声明。注册应支持清理，并明确处理中途注销的行为。

这并不意味着用户可以随便改底层保留前缀、协议编号或字节上限。扩展业务与改动协议是两回事。

### 5. 分片与流式的约定

分片层只处理一条已编码的逻辑消息，记录所属消息、片段次序和完成条件。它不解析“审批是否通过”或“文本是什么角色”。

流式层处理连续产生的数据，记录所属流、顺序和结束状态。正常完成、失败、取消应互斥且最多发生一次；终止后的迟到数据按固定规则忽略或报错，不能继续更新已经结束的结果。

先实现有界缓冲、总量限速、过载错误和可取消任务。若使用场景确实需要接收方控制发送速度，再协商增加“还可接收多少条数据”的额度消息。额度按逻辑数据条目计算，不能因为某条数据拆成三片就扣三次；但还必须有独立的字节上限，避免一条数据就吃满内存。

取消表示请求对方停止后续工作，并不保证撤销已经执行的游戏操作。断线后也不能承诺恰好执行一次。

### 6. 不要先赌某种编码一定更快

先保留容易调试的 JSON 逻辑表示，优先减少重复元数据和无意义的嵌套。具体线格式是否使用短键、分隔符或其他编码，应通过相同内容的实测再决定。

下行字节预算必须计算最终命令行，包括命令前缀、消息头、JSON 转义和实际内容；上行另按聊天载体限制检查。不能只测业务正文，也不能把二进制编码后再套文本编码的开销忽略掉。

建议比较中文、表情、引号、长功能名、长元数据、大快照与连续小片段；记录总字节数、命令数、第一段到达时间、完整完成时间、内存峰值和过载行为。当前尚未做游戏实机性能测试，因此这里不宣称新方案已经更快。

## 七、日志应该怎样清晰而不吵

保留两种观察视角：

| 视角 | 记录什么 | 使用场景 |
| --- | --- | --- |
| 通信记录 | 收发方向、连接、时间、实际字节数、实际数据包 | 排查协议、分片和编码问题 |
| 操作记录 | 玩家、功能名称、请求编号、traceId、耗时、结果 | 追踪一次用户操作 |

完整数据包记录应是可配置能力，可指定连接或请求进行诊断，并支持脱敏；普通运行日志默认记录摘要。方向可使用“服务端到游戏／游戏到服务端”，避免观察位置不同造成歧义。

原始发送记录还应区分“准备发送”“传输成功”“发送失败”，不能把发送前事件叫作已经送达。传输成功同样不代表业务执行完成。

对于回声，先区分玩家消息、桥接消息、系统回声和命令确认，再决定日志级别。不能按文本相同就删除，也不能丢弃所有命令确认，因为其中一些正等待与请求配对。已知回声可在普通日志中降级，在诊断模式下保留。

## 八、建议的重构顺序

| 阶段 | 做什么 | 完成标准 |
| --- | --- | --- |
| 第一阶段：收发运行 | SDK 管理业务任务；统一原生命令等待、断连清理和发送调度 | 回调中等待回复不会饿死接收；慢玩家不拖住其他玩家；关键消息不静默丢失 |
| 第二阶段：模块整理 | 抽出通用重组逻辑；把会话、审批、文本显示整理为可选扩展；提供逐项路由注册 | 新增一个业务功能无需修改总入口与分片层；旧协议测试继续通过 |
| 第三阶段：新协议 | 固定统一封套、元数据、双向分片、错误规则与版本协商 | Python 与附加包交叉测试通过；未知可选字段可往返；不支持的版本明确拒绝或回退 |
| 第四阶段：真正流式 | 支持持续数据、结束、取消和有界缓冲，再按实测需要增加接收额度 | 未知总长度也能开始发送；取消不泄漏任务；慢接收方不会无限积压 |

第一、二阶段尽量保持当前线格式；不能为了统一模型，把旧协议原子会话回复偷偷改成新分片格式。第三阶段涉及双方协同升级，应作为明确的新协议版本发布。

建议先用一个真实功能贯穿新路径，例如“查询背包”：普通玩家消息触发、登记请求、发送命令、附加包处理、分片回复、恢复等待、输出日志、断连清理。这个路径稳定后再迁移其他功能。

## 九、迁移时需要守住的规则

旧版本的清单和测试样本保持不变，新版本有自己的固定约定。不要把现有只读协议配置突然变成任意可替换的字典，否则 Python 与附加包很容易各说各话。

新旧版本并存时，使用清晰可识别的版本或通道。普通游戏聊天在没有附加包时仍可用；附加包能力按握手结果启用。旧端不理解新握手时，可以通过一次有超时的探测确认兼容模式，不能无限等待或反复探测。

开发者使用稳定的高层连接接口；兼容层负责旧协议与新内部模型之间的转换。不要要求每个宿主自行识别五种旧格式。

附加包仍然不是安全边界。宿主负责身份认证与授权，桥接前缀和假人名称只帮助分类。迁移测试涉及启用附加包时，世界必须开启“实验性功能 → Beta APIs”，否则脚本不会加载，不能把这种超时误判成新协议不兼容。

## 十、必须补上的验收场景

1. **回调内请求。** 玩家回调、连接建立回调、界面消息回调中等待请求，都不会阻止接收回复。
2. **隔离与顺序。** 同一玩家按约定保持顺序；不同玩家可并行；不同连接使用相同请求编号也不会串包。
3. **生命周期。** 断连、超时、取消、发送失败后，请求表、业务任务与分片缓冲均能清理。
4. **过载。** 一名玩家或一个大请求不能耗尽整条连接；关键消息有明确错误或等待语义。
5. **双向分片。** 中文、表情、引号、乱序、重复、冲突片段、缺失片段及超大消息都有确定结果。
6. **扩展字段。** 两端往返保留未知可选元数据；错误类型与业务结果不混淆。
7. **真正流式。** 不知道总长度时就开始发送；结束和取消只生效一次；迟到片段不会恢复已结束的流。
8. **诊断。** 慢日志接收器不阻塞收发；可根据同一 traceId 还原操作链；回声过滤不误吞命令回复。
9. **兼容。** 新服务端配旧附加包、旧服务端配新附加包、没有附加包三种情况都给出明确行为。
